# Code audit, September 2026

*26 September 2026 · commit `994a6d8` (main)*

A whole-repository audit done before the Expo migration: ten parallel review passes (database performance, background jobs and concurrency, security, data model, business logic, views and code structure, test quality, a full test run, settings and deployment, frontend and PWA), a stack assessment, and an independent Codex review. The most severe findings were checked against the code by hand.

## Summary

- **Tests:** 349 unit and 27 end-to-end tests pass, none skipped. `ruff check` and `ruff format --check` are clean; `makemigrations --check` finds no drift; `check --deploy` passes (HSTS preload silenced on purpose); `pip-audit` finds no known vulnerabilities.
- **Authorization:** no view lets one gym's coach or athlete read or change another's data. Every coach view uses `coach_required` and `coach_athlete()`; every athlete view scopes by `request.athlete`; library objects scope by gym. Invite tokens are 144-bit, expire after 14 days and are single-use.
- **Business rules:** e1RM, plate rounding, worked-from maxes, template layout and progressive weeks match `docs/BUILD_PLAN.md`.
- **Where the problems are:** the rate limiter, offline logging in the PWA, undo, alert de-duplication, the demo re-seed, dashboard query volume, and a set of smaller logic bugs listed below.

## Codex compared with the Claude passes

Both flagged the compliance window (M1), dashboard query fan-out (H4), oversized view files and phase-named test files, and both recommended keeping Django as the backend with an Expo app for athletes. Codex alone found the cross-athlete alert collision (H1) and fixed-weight rounding (M3); both were confirmed by hand. The Claude passes alone found every Critical item, the undo bugs, the digest failure mode and the data-model cascades.

## Stack assessment (summary)

The backend is the valuable, well-separated part: service modules import no request or template code, and roughly 65–70% of the Python survives an API-first rebuild (models, services, admin, most unit tests). Options weighed: improve the PWA; wrap it in Capacitor or Hotwire Native; Django API plus an Expo app; a full TypeScript rewrite. With offline as a hard requirement and one front end for three platforms, the owner chose Django API plus a single Expo app. The reasoning and rejected alternatives are in the decision log in `docs/EXPO_MIGRATION.md`.
